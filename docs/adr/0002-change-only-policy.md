# ADR-0002: Change only policy between runs

- **Status:** accepted
- **Date:** 2026-11-03

## Context

The headline claim is "identity-based segmentation shrank what a compromised
workload can reach." That claim is only as good as the experimental control.
If anything besides policy differs between the baseline and hardened runs (a
patched app, a removed RBAC binding, a lower IMDS hop limit, a firewall), a
Denied row can no longer be attributed to policy.

## Decision

The baseline and hardened runs share the same cluster, Cilium install, app
image, foothold, ServiceAccounts, RBAC, node metadata settings, security groups
and DNS config. The only difference is the set of `NetworkPolicy` and
`CiliumNetworkPolicy` objects in the three lab namespaces. The runner applies a
profile by deleting every policy object in those namespaces and applying the
profile directory, and touches nothing else. The baseline is an explicit
allow-all `CiliumNetworkPolicy`, not "no policy", so the engine is provably
loaded in both runs.

Corollaries:

- The planted RCE keeps working after hardening. The headline is that the
  attacker still runs commands; what changes is what those commands can reach.
- The foothold has no RBAC from the start (no token mounted, no Role, no
  RoleBinding), so it cannot edit policy or relabel itself in either run. The
  runner proves this with `kubectl auth can-i` before trusting any result.
- Exfil markers are generated by the runner per run, never read from the
  sensitive service, so blocking sensitive access cannot prevent the egress
  scenarios from running.
- No firewall layer (AWS Network Firewall, Route 53 Resolver DNS Firewall,
  restrictive egress security groups) is added, because it would also deny
  the egress rows. Those belong in production as defense in depth (README,
  Production scale), and could be measured as a separate profile later.

One infra setting exists only to keep that true on EKS: under Cilium ENI IPAM,
pods carry the node security group, so the node group trusts itself on all
ports. Otherwise the security group, not the policy, decides which cross-node
pod flows work (the first live run lost the DNS row this way).

## Alternatives rejected

| Option | Why not |
| ------ | ------- |
| Harden everything at once (policy + IMDS hop limit + firewall) | Stronger end state, but the matrix could not say which control did the work. |
| Baseline with no policy objects | Valid, but leaves "was Cilium even enforcing?" open. An allow-all policy closes it. |
| Separate clusters for baseline and hardened | Two clusters differ in pod IPs, identities and timing; one cluster with a policy swap is the cleaner control. |

## Consequences

The node keeps IMDS hop limit 2 in both runs, which a production node would
not. That is a deliberate measurement choice, stated in `infra/eks.tf` and the
README. Any future control (firewall, Security Groups for Pods) gets its own
profile column rather than being folded into "hardened".
